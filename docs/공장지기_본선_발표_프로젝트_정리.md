# 공장지기 본선 발표용 프로젝트 정리

작성일: 2026-05-22  
대상: 2026 스마트 공장 운영 시스템 MVP 개발 해커톤 본선 발표  
프로젝트명: 공장지기  
한 줄 정의: 설비 센서 데이터로 잔여수명(RUL)과 72시간 내 고장 위험도를 추정하고, 그 근거를 매뉴얼 기반 정비 작업지시서로 변환해 작업자에게 전달하는 중소 제조사 전용 AI 운영 플랫폼

---

## 1. 발표에서 가장 먼저 말할 핵심

공장지기는 단순한 대시보드가 아니라, 설비 상태를 감지하고, 고장 위험을 추정하고, 정비 지시를 생성하고, 작업 결과를 다시 데이터로 축적하는 폐쇄 루프 운영 시스템이다.

핵심 메시지는 다음 3가지다.

| 메시지 | 발표 표현 |
|---|---|
| 문제 | 중소 제조 현장은 고장이 난 뒤에야 대응하고, 숙련자 노하우가 사람에게만 묶여 있다. |
| 해결 | 센서 기반 RUL/위험도 추정 결과를 작업자가 바로 실행할 수 있는 정비 지시서로 바꾼다. |
| 차별점 | AI 예측에서 끝나지 않고, 작업 결과를 학습 데이터와 월간 노하우 리포트로 축적한다. |

30초 엘리베이터 피치:

```text
공장지기는 중소 제조사의 설비 고장을 사전에 줄이기 위한 AI 운영 플랫폼입니다.
진동, 온도, 전류, 유압 같은 센서 흐름을 바탕으로 설비의 잔여수명과 72시간 내 위험도를 추정하고,
그 결과를 설비 매뉴얼과 과거 정비 이력에 연결해 작업자가 바로 실행할 수 있는 정비 작업지시서로 바꿉니다.
작업자가 결과를 입력하면 이 데이터가 다시 정비 이력과 학습 큐로 쌓여,
한 번의 예측이 아니라 공장 안의 노하우가 계속 축적되는 폐쇄 루프를 만듭니다.
```

주최: DACON + 차세대융합기술연구원

발표에서 강조할 프레이밍:

- "고장 시점을 정확히 맞힌다"가 아니라 "잔여수명과 위험도를 확률/구간으로 추정한다."
- "AI가 정비를 대체한다"가 아니라 "AI가 숙련자의 판단을 구조화하고 작업자가 실행 가능한 지시로 바꾼다."
- "완성형 상용 모델"이 아니라 "MVP에서 예측-지시-축적 루프가 작동함을 검증했다."

## 3. 문제 정의

대상 현장:

- 경기도 중소 제조사
- 자동차 부품 사출성형 공장
- 노후 사출기와 비교적 신형 설비가 혼재
- 사무실 공용 PC와 스마트폰 중심의 운영 환경
- 정비 기록은 종이 점검표, 숙련자 경험, 구두 지시 중심

가상 페르소나:

| 항목 | 내용 |
|---|---|
| 이름 | 김영수 반장 |
| 연령/경력 | 48세, 생산팀장 12년차 |
| 현장 | 경기도 시흥시 시화공단 자동차 부품 사출성형업체 |
| 설비 | 사출기 8대, 1996~2018년식 혼재 |
| 도구 | 스마트폰, 카카오톡, 사무실 공용 PC, 종이 점검표 |
| KPI | 월 가동률 95% 이상, 납기 지연율 2% 이하 |

문제 시나리오:

| 날짜 | 사건 | 운영상 손실 |
|---|---|---|
| 4/8 03:22 | 3호 사출기 유압 펌프 고장 | 36시간 비계획 정지 |
| 4/12 | 고객사 납기 지연 페널티 발생 | 800만 원 페널티 가정 |
| 4/15 | 베테랑 정비기사 퇴사 통보 | 암묵지 손실 |
| 4/22 | 신입 작업자에게 모호한 정비 지시 | 실행 품질 편차 |

중요한 발표 주의:

- 김영수 반장은 실제 인터뷰 인물이 아니라 산업 현장 문제를 설명하기 위한 가상 페르소나다.
- 36시간, 800만 원, 연 절감액 등은 MVP 효과를 설명하기 위한 시나리오 가정값이다.
- 본선 답변에서는 "파일럿에서 실측 검증할 목표값"이라고 명확히 말하는 편이 안전하다.

## 4. 솔루션 개요

공장지기는 다음 3개 모듈로 구성된다.

| 모듈 | 역할 | 입력 | 처리 | 출력 |
|---|---|---|---|---|
| A. 추정 | 센서 -> RUL/위험도 | 진동, 유압 온도, 모터 전류, 유압 압력 | RUL 회귀 + 고장 분류 + 근거 센서 산출 | RUL, 위험도, 고장 후보, 근거 센서 |
| B. 지시 | 추정 결과 -> 작업지시서 | RUL, 위험도, 설비 모델, 매뉴얼, RAG 검색 결과 | Gemini 또는 템플릿 생성기 | 단계별 작업지시서, 안전수칙, 부품 목록 |
| C. 축적 | 정비 결과 -> 운영 지식 | 작업 완료 결과, 실제 고장 유형, 소요 시간, 메모 | DB 저장 + 학습 큐 생성 + 월간 집계 | 노하우 리포트, 재학습 데이터 |

전체 데이터 흐름:

```text
센서 tick 생성
-> sensor_readings 저장
-> prediction_runs 생성
-> equipment_state_latest 갱신
-> 대시보드/WebSocket 반영
-> 작업지시서 생성
-> 카카오톡 전송 데모
-> 정비 결과 입력
-> maintenance_records + learning_queue 저장
-> 월간 노하우 리포트 반영
```

## 8. AI 모델 상세

### 8.1 RUL 회귀 모델

역할:

- 설비가 앞으로 얼마나 더 정상 가동 가능할지 잔여수명(RUL)을 추정한다.
- RUL을 기반으로 72시간 내 고장 위험도를 계산한다.
- 결과는 `rul`, `rulMin`, `rulMax`, `risk`로 프론트에 표시된다.

사용 데이터:

| 항목 | 내용 |
|---|---|
| 데이터셋 | NASA C-MAPSS |
| 성격 | 터보팬 엔진 열화 시뮬레이션 데이터 |
| 입력 | unit, cycle, operational setting 3개, sensor 21개 |
| 사용 subset | FD001, FD002, FD003, FD004 |
| window | 50 cycle |
| feature | sensor 21 + condition one-hot 6 + subset one-hot 4 = 31개 |
| RUL cap | 125 cycle |

모델:

| 모델 | 역할 |
|---|---|
| GRU | 안정적인 시계열 baseline |
| TCN | temporal convolution 기반 보완 |
| PatchTST | Transformer 계열 시계열 후보 |
| 앙상블 | seed 42 기준 GRU 0.30, TCN 0.35, PatchTST 0.35 |

검증 결과:

| 항목 | 결과 |
|---|---:|
| validation 기반 seed 평균 RMSE | 약 12.738 |
| seed 42 official RMSE | 12.614 |
| FD001 RMSE | 12.674 |
| FD002 RMSE | 12.492 |
| FD003 RMSE | 12.231 |
| FD004 RMSE | 12.865 |
| API inference 평균 | 31.8ms |
| API inference p95 | 48.2ms |

발표 시 주의:

- C-MAPSS는 항공 엔진 데이터이므로 사출기에 그대로 적용한다고 말하면 안 된다.
- MVP에서는 RUL 회귀 파이프라인, 검증 방식, API 연동 구조를 증명한 것이다.
- 실제 사출기 적용은 Phase 1 파일럿 데이터로 보정/재학습해야 한다.

### 8.2 고장 분류 모델

역할:

- 설비가 정상인지 고장 위험인지 판단한다.
- 고장일 경우 베어링 불량, 회전체 불평형, 축정렬 불량, 벨트 느슨함 등의 원인 후보를 제시한다.
- Top-1 확정 진단이 아니라 Top-3 추정 후보로 표현하는 것이 안전하다.

사용 데이터:

| 항목 | 내용 |
|---|---|
| 데이터셋 | AI-Hub 238 기계시설물 고장 예지 센서 |
| 대상 | 전동기 기반 기계시설물 |
| 라벨 | 정상, 베어링 불량, 회전체 불평형, 축정렬 불량, 벨트 느슨함 |
| 신호 | 전류, 진동 |

검증 결과:

| 항목 | 결과 |
|---|---:|
| 전류 기반 정상/고장 group-CV accuracy mean | 약 0.800 |
| 전류 기반 정상/고장 group-CV macro F1 mean | 약 0.721 |

제품 적용 정책:

| 판단 | 발표 표현 |
|---|---|
| 정상/고장 | MVP 알림 신호로 사용 가능 |
| 고장 유형 | 확정 진단이 아니라 원인 후보 Top-3로 제시 |
| 미지 패턴 | 낮은 confidence 또는 unknown anomaly는 점검 필요로 안내 |

### 8.3 현재 백엔드 추론 런타임

현재 `backend/app/ml/handoff_runtime.py`는 다음 흐름을 가진다.

```text
최근 센서 포인트 로드
-> 50개 window로 padding/crop
-> 4개 현장 센서로 degradation profile 산출
-> C-MAPSS형 synthetic feature window 생성
-> 저장된 GRU/TCN/PatchTST checkpoint가 있으면 앙상블 추론
-> checkpoint를 못 읽으면 surrogate RUL 계산
-> AI-Hub joblib registry가 있으면 정상/고장 및 고장 후보 추론
-> joblib를 못 읽으면 surrogate fault probability 계산
-> risk, status, root sensors 반환
```

이 구조 덕분에 시연 안정성이 높다.

- 모델 artifact가 있으면 실제 학습 산출물을 사용한다.
- artifact 또는 라이브러리가 빠져도 surrogate/fallback으로 화면 흐름이 깨지지 않는다.
- `raw_output`에 어떤 mode로 추론했는지 기록해 재현성과 디버깅이 가능하다.

## 9. LLM + RAG 작업지시서

작업지시서 생성 흐름:

```text
설비 최신 상태 조회
-> 최신 prediction/root sensors 조회
-> 설비 모델과 고장 후보로 매뉴얼 chunk 검색
-> Gemini 또는 template generator 실행
-> work_orders / steps / parts / sources 저장
-> 프론트에 작업지시서 표시
```

출력 항목:

| 항목 | 예시 |
|---|---|
| 제목 | 3호 사출기 예방 정비 작업지시서 |
| RUL | 72h (±24h) |
| 위험도 | 78% |
| AI 진단 | 베어링 불량 (78%) |
| 근거 센서 | 진동 RMS 상승, 모터 전류 변동성, 유압 온도 상승 |
| 절차 | 안전, 진단, 윤활, 부품, 복구, 기록 |
| 소요 시간 | 약 65분 |
| 필요 부품 | Mobilux EP 2 그리스, 베어링 #6205-2RS 등 |
| 안전수칙 | 전원 차단, LOTO, 유압 잔압 해제 |
| 출처 | 설비 운영 매뉴얼 chunk |

LLM provider:

| provider | 상태 |
|---|---|
| `template` | 기본값, 외부 API 없이 안정 시연 가능 |
| `gemini` | `GEMINI_API_KEY` 설정 시 실제 Gemini API 호출 |
| fallback | Gemini 실패/키 누락/응답 파싱 실패 시 template로 자동 fallback |
| `openai` | 설정 필드는 있으나 generator는 아직 미구현 |

발표용 메시지:

```text
예측 결과를 보여주는 데서 끝나면 현장 작업자는 다시 판단해야 합니다.
공장지기는 RUL, 고장 후보, 근거 센서를 매뉴얼과 연결해
```

## 18. 본선 예상 질문과 답변

### Q1. 실제 사출기 데이터로 학습했나요?

아닙니다. MVP 단계에서는 실제 사출기 데이터를 대량 확보하기 어렵기 때문에, RUL 회귀는 NASA C-MAPSS로 파이프라인과 검증 방식을 확인했고, 고장 분류는 AI-Hub 기계시설물 센서 데이터로 정상/고장 및 원인 후보 분류를 검증했습니다. 실제 적용은 Phase 1 파일럿에서 현장 데이터로 보정/재학습하는 구조입니다.

### Q2. C-MAPSS는 항공 엔진인데 사출기에 맞나요?

그대로 맞다고 주장하지 않습니다. C-MAPSS는 RUL 회귀 문제를 검증하기 위한 표준 벤치마크로 사용했습니다. 공장지기에서 중요한 것은 "센서 window -> RUL/위험도 -> 작업지시서 -> 결과 축적"이라는 운영 파이프라인이며, 실제 사출기 적용 시에는 파일럿 데이터로 모델을 보정합니다.

### Q3. 고장 유형 분류 정확도가 충분한가요?

정상/고장 판단은 MVP 알림 신호로 사용할 수 있는 수준까지 검증했습니다. 다만 고장 유형은 Top-1 확정 진단으로 말하지 않고, Top-3 원인 후보와 근거 센서를 함께 제시하는 방식으로 설계했습니다. 현장에서는 이 방식이 과도한 확신보다 안전합니다.

### Q4. Gemini API가 실패하면 시연이 멈추나요?

아닙니다. 작업지시서 generator는 `template` fallback을 갖고 있습니다. Gemini API key가 없거나 호출 실패, 응답 파싱 실패가 발생해도 템플릿 생성기로 작업지시서가 생성되어 시연 흐름은 유지됩니다.

### Q5. 카카오톡은 실제 전송인가요?

MVP에서는 데모 전송입니다. 실제 카카오 비즈메시지 연동은 운영 단계에서 붙일 수 있도록 `send-kakao` API와 상태 전환 구조를 먼저 구현했습니다.

### Q6. 플랫폼이라는 말이 과장 아닌가요?

공장지기는 화면 모음이 아니라 운영 루프를 완결합니다. 센서 수집, AI 추정, 지시서 생성, 작업자 전달, 결과 입력, 리포트/학습 큐 축적이 하나의 흐름으로 연결되어 있기 때문에 플랫폼이라고 정의했습니다.

### Q7. 기대 효과 수치는 실측인가요?

아닙니다. 현재 수치는 데모 시나리오와 목표값입니다. 본선에서는 "MVP 완성 후 경기도 중소 제조사 파일럿에서 실제 정지시간, MTTR, 고장 미탐률, 불필요 정비율을 검증하겠다"고 답하는 것이 정확합니다.

### Q8. 왜 중소 제조사에 적합한가요?

중소 제조사는 대규모 MES나 전용 앱을 바로 도입하기 어렵습니다. 공장지기는 웹 대시보드와 카카오톡 흐름을 중심으로 하고, 초기에는 시뮬레이터/CSV로도 운영 루프를 검증할 수 있게 설계했습니다. 진입 장벽을 낮추는 것이 핵심입니다.

## 19. 발표 금지 표현과 권장 표현

| 피해야 할 표현 | 권장 표현 |
|---|---|
| 고장 시점을 정확히 예측합니다. | 잔여수명과 72시간 내 위험도를 구간/확률로 추정합니다. |
| AI가 고장 원인을 확정합니다. | AI가 고장 원인 후보와 근거 센서를 제시합니다. |
| C-MAPSS 모델을 사출기에 바로 적용합니다. | C-MAPSS로 RUL 파이프라인을 검증했고, 현장 파일럿으로 보정합니다. |
| 페르소나 인터뷰 결과입니다. | 산업 현장 문제를 반영한 가상 페르소나 시나리오입니다. |
| 비용이 전혀 들지 않습니다. | MVP는 무료/저비용 구성을 우선했고, 운영 전환 시 API/인프라 비용을 최적화합니다. |
| 카카오톡 실전 연동 완료입니다. | MVP에서는 카카오톡 전송 데모이며, 운영 API 연동 가능 구조를 마련했습니다. |

```text
그 결과를 다시 현장 노하우로 축적하는 중소 제조사형 AI 예지보전 플랫폼입니다.
```
